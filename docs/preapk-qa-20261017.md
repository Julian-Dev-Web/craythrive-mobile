## Issues fixed

The first full run exposed six failing suites. Their fixtures had fallen behind
the current code: missing auth initialization/session hooks, recreated `useRef`
objects, assumptions about state/interval positions, obsolete ammonia insert
responses, a missing server-clock mock and an expectation of Critical severity
without configured Critical limits. The fixtures now exercise the current paths
and retain assertions for duplicate prevention, scoped reads/writes, failure retry,
cleanup and honest missing-configuration feedback.

TypeScript also found an optional Back callback treated as required. `AppScreen`
now declares its existing optional behavior explicitly. The mobile TypeScript
project excludes the server-side Deno functions and saved build archive; Edge
Function behavior remains covered separately by its isolated suites.

The first visual matrix found 16 overflow cases across five screens:

- Registration section descriptions did not have a bounded flexible column.
- Password-reset inputs could push their eye controls outside a narrow row.
- Add Listing quantity inputs could exceed their two-column field width.
- The manual ammonia input could push its `ppm` suffix out at larger text sizes.
- The threshold section’s Synced badge could extend past the screen edge.

The fixes add flexible text columns, allow inputs to shrink within their rows,
and let the threshold header wrap. Font scaling stays enabled. The final same
192-case matrix detected no horizontal overflow.

WiFi setup was also made easier to reach: Check WiFi Status now comes before the
status details. Empty status placeholders no longer fill the first screen.
Saved network names, firmware and cloud details expand through Saved Networks &
Device Details, leaving the WiFi form higher on the page. Its API/heartbeat and
Forget confirmation behavior still pass the WiFi interaction suite.

## Repeat the checks before a later build

New commands:

```powershell
npm.cmd run typecheck
npm.cmd run qa:modules
npm.cmd run qa:ui
```

`npm.cmd run qa` combines TypeScript and module suites. The module runner fails
when any suite fails or is skipped, and writes each suite's output to the QA log
directory. The SQL suite requires an existing PGlite installation. For this run,
the already available external installation was selected without changing app
dependencies:

```powershell
$env:PGLITE_MODULE = 'C:/Users/AMD/AppData/Local/Temp/craythrive-sql-validation/node_modules/@electric-sql/pglite'
npm.cmd run qa
```

On another machine, set `PGLITE_MODULE` to its own PGlite installation. Browser QA
uses Chrome or Edge; set `MOBILE_QA_CHROME` if the executable is elsewhere.

The final Android export used:

```powershell
$env:EXPO_OFFLINE = '1'
node node_modules/expo/bin/cli export --platform android --output-dir .expo/preapk-qa/android-export --max-workers 2
```

This exports JavaScript/Hermes and assets; it does not compile or install an APK.

## Physical-phone and live-service acceptance still required

Use dedicated test accounts and a test tank on a real Android phone:

1. Install a preview APK. Check light/dark mode, larger system text, gesture and
   three-button navigation, every tab, long names, scrolling, keyboard and Back.
2. Log in, background/reopen and relaunch. Test failed/offline login and restoration,
   registration verification, a password-reset link, profile/avatar save and logout.
3. Create breeder/juvenile tanks; test invalid values and rapid Create taps. Pair
   each board, verify fresh readings and configured thresholds across Dashboard,
   Tank Details, Reports and AI. Unpair and verify former sensor data is not reused.
4. Run both boards through [the two-hotspot WiFi procedure](esp32-wifi-recovery.md#hardware-test-procedure-two-phone-hotspots-both-devices),
   including wrong passwords, old-hotspot loss, backup recovery and Forget vs Unpair.
5. Grant/deny camera and photo access. Scan a real strip under suitable lighting,
   test manual input, save once, retry a failed save and verify the returned saved
   row/timestamp across screens.
6. With buyer/seller test accounts, publish/edit an item, reserve/cancel, send/read
   chat, check order statuses, and test simultaneous buyers against deployed server
   constraints. Client-only reservation locks do not establish cross-buyer atomicity.
7. Exercise the deployed AI service with a real tank, an unrelated question and a
   threshold preview. Cancel first, then confirm once on a test tank; verify saved
   values and ownership restrictions using the actual backend.
8. Verify deployed push configuration and real alert creation/deduplication. Test
   foreground, background and closed-app delivery, tap routing, preferences and
   logout on the installed APK.

No cloud APK build was started in this pass. No connected device was available
for native testing. Local QA is green; release acceptance depends on those live
and hardware checks.
